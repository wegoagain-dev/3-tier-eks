# Production Grade Three-Tier App on AWS EKS including RDS, GitOps (ArgoCD), Prometheus, Grafana, Github Actions

## Overview

This project deploys a three-tier application on AWS EKS using a highly available, production-grade architecture spanning multiple availability zones. The application consists of a React frontend, Flask backend and a RDS PostgreSQL database. It demonstrates end-to-end DevOps practices with containerisation, CI/CD automation, and GitOps deployment with ArgoCD.

The app is a DevOps related quiz application where users can take quizzes on various DevOps topics, you can also add your own `.csv` files to make your custom quizzes.

I have a detailed guide on how to deploy this application on AWS EKS on my blog [here](https://wegoagain.dev/blog/3-tier-eks-microservices).

## Key Features

Infrastructure as Code with Terraform covering the VPC, EKS cluster, RDS database, IAM roles, and even Kubernetes namespaces and secrets. One terraform apply brings up the entire environment and one terraform destroy tears it all down. No clicking around the AWS console and no forgotten resources.

The EKS cluster runs across multiple availability zones with managed node groups. AWS handles the node lifecycle and AMI updates while I control instance types and scaling. This hits the sweet spot between Fargate, which costs more for sustained workloads, and self-managed nodes which require SSH access for maintenance.

GitOps deployment through ArgoCD means any changes pushed to the Kubernetes manifests get synced to the cluster automatically. Combined with GitHub Actions for CI/CD, the workflow becomes push code and watch it deploy.

Observability comes from Prometheus and Grafana for monitoring cluster health and application metrics.

Security is implemented through multiple layers. GitHub Actions authenticates with AWS using OIDC so there are no long-lived credentials stored in GitHub Secrets. IRSA, IAM Roles for Service Accounts, allows individual pods to assume IAM roles rather than giving all pods on a node the same permissions. The database password is generated by Terraform and stored in AWS Secrets Manager, never hardcoded. RDS sits in isolated database subnets with no internet access and only accepts connections from the EKS node security group.

## Architecture

![](./images/eks-devopsquiz.png)

The network layout uses three tiers of subnets. Public subnets host the ALB and allow internet access. Private subnets run the EKS nodes and reach the internet through a NAT Gateway. Database subnets are completely isolated with no internet access at all. Using a single NAT Gateway saves about thirty dollars per month for development environments while still providing the necessary connectivity.

## Cost Considerations

Running this infrastructure on AWS costs roughly one hundred ninety dollars per month. The EKS control plane accounts for seventy three dollars, two t3.medium EC2 nodes run about sixty dollars, the RDS PostgreSQL database is thirteen dollars, the NAT Gateway is thirty two dollars, and the ALB is sixteen dollars. These prices are based on eu-west-2 London region. Remember to run terraform destroy when finished experimenting to avoid ongoing charges.

## Prerequisites

You will need **aws cli**, **kubectl**, **terraform**, and **docker** installed locally. I am assuming you have basic familiarity with Kubernetes and AWS.

## CI/CD and GitOps Workflow

![](./images/workflow.svg)

The pipeline starts when code is pushed to GitHub. GitHub Actions builds the Docker images and runs Trivy vulnerability scanning. If Trivy finds any CRITICAL vulnerabilities, the build fails immediately. Once the scans pass, images get pushed to ECR and the workflow updates the Kubernetes manifests with the new image tags, then commits those changes back to the repository.

ArgoCD watches the repository and automatically syncs any changes to the cluster. This means deploying new code is as simple as git push. No manual kubectl apply commands and no SSHing into servers.

Authentication uses OIDC for both GitHub Actions and the EKS cluster itself. GitHub Actions exchanges short-lived tokens for AWS credentials without storing long-term access keys. The EKS cluster uses IRSA so pods can assume specific IAM roles rather than inheriting broad permissions from the underlying EC2 nodes.

## How to Run

### Option 1: Run Locally (Docker Compose)

The most efficient way to run the entire stack locally is using **Docker Compose**. This will start the database, run migrations, and launch both the backend and frontend.

```bash
# Clone the repository
git clone https://github.com/wegoagain-dev/3-tier-eks.git
cd 3-tier-eks

# Start the entire stack
docker compose up --build -d
```

Once started:

- **Frontend:** [http://localhost:8080](http://localhost:8080)
- **Backend API:** [http://localhost:8000/api](http://localhost:8000/api)

### Option 2: Deploy to AWS (GitOps with ArgoCD)

For the full production deployment on AWS, check out the detailed guide [here](https://wegoagain.dev/blog/3-tier-eks-microservices).

**1. Configure Terraform Backend:**
Before running Terraform, you need to configure the backend state.

- Create an S3 bucket in your AWS account.
- Update `terraform/provider.tf` with your bucket name and region:
  ```hcl
  backend "s3" {
    bucket       = "your-unique-bucket-name"
    key          = "dev/terraform.tfstate"
    region       = "eu-west-2"
    encrypt      = true
  }
  ```
- _Alternatively_, for testing, you can comment out the `backend "s3"` block to use local state.

**2. Provision Infrastructure:**
This step creates the VPC, EKS Cluster, RDS Database, and installs ArgoCD.

```bash
cd terraform
terraform init
terraform apply
```

_Note: This process takes approximately 15-20 minutes._

**3. Configure kubectl:**
Once Terraform finishes, update your kubeconfig to interact with the new cluster:

```bash
aws eks update-kubeconfig --name devops-quiz --region eu-west-2
```

**4. Deploy Application via ArgoCD:**
Apply the ArgoCD application manifest to start the GitOps workflow:

```bash
kubectl apply -f argocd-app.yaml
```

ArgoCD will automatically sync the `k8s/` directory to your cluster.

**5. Access ArgoCD UI:**

```bash
# Get password
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath="{.data.password}" | base64 -d; echo

# Port-forward
kubectl port-forward svc/argocd-server -n argocd 9000:443
```

Open [https://localhost:9000](https://localhost:9000)

**To Deploy Changes:**
Just `git push`! ArgoCD watches the repo and updates the cluster automatically.

### Option 3: Kubernetes (Kind)

You can also run the full Kubernetes stack locally using `kind`.

1. **Create the Cluster:**

   ```bash
   kind create cluster --name three-tier --config kind-config.yaml
   ```

2. **Build Container Images:**

   **Using Docker:**

   ```bash
   docker build -t 3-tier-eks-backend:latest ./backend
   docker build -t 3-tier-eks-frontend:latest ./frontend
   ```

3. **Load Images into Kind:**

   **Using Docker:**

   ```bash
   kind load docker-image 3-tier-eks-backend:latest --name three-tier
   kind load docker-image 3-tier-eks-frontend:latest --name three-tier
   ```

4. **Create Secrets:**

   ```bash
   # Copy the example file and update if needed
   cp .env.k8s.example .env.k8s

   # Create the secret from the env file
   kubectl create secret generic database-secret \
     --from-env-file=.env.k8s \
     --namespace 3-tier-app-eks
   ```

5. **Apply Manifests:**

   ```bash
   # Apply Namespace and ConfigMaps
   kubectl apply -f k8s-local/namespace.yaml
   kubectl apply -f k8s-local/configmap.yaml
   kubectl apply -f k8s-local/postgres.yaml

   # Wait for the database to be ready, then apply the rest
   kubectl wait --namespace 3-tier-app-eks \
     --for=condition=ready pod \
     --selector=app=postgres \
     --timeout=90s

   kubectl apply -f k8s-local/
   ```

6. **Access the Application:**
   Since we aren't using an Ingress Controller locally, use port-forwarding:

   ```bash
   # Frontend (Access at http://localhost:8080)
   kubectl port-forward svc/frontend -n 3-tier-app-eks 8080:80

   # Backend (Access at http://localhost:8000)
   kubectl port-forward svc/backend -n 3-tier-app-eks 8000:8000
   ```

## Troubleshooting

### Migration Job Failures

Check logs with kubectl logs -f database-migration-<pod-name> -n 3-tier-app-eks. Verify the database is ready using kubectl get pods -n 3-tier-app-eks -l app=postgres. Check that secrets exist with kubectl get secret database-secret -n 3-tier-app-eks -o yaml.

### Ingress Stuck Without ADDRESS

The AWS Load Balancer Controller needs the correct IAM policy. If you are using a v2.7 policy but the Helm chart installed v3.0 of the controller, the ingress will never get an address. Always fetch the policy from the main branch so it matches your controller version.

### Frontend Shows Connection Error

This happens when the React app has localhost:8000 hardcoded during development. The fix is to use a relative path like /api which the ALB ingress routes correctly based on the path rules.

### Architecture Mismatch on EKS

Building Docker images on an M1 Mac creates ARM architecture images but EKS nodes run x86. The pods crash with exec format error. Build images with docker buildx build --platform linux/amd64 to target the correct architecture for EKS nodes.

## Cleanup & Teardown (AWS)

> **⚠️ IMPORTANT**: Follow these steps to avoid unexpected AWS charges.

### AWS Deployment Cleanup

**Step 1: Delete Ingress (triggers ALB cleanup)**

```bash
kubectl delete ingress three-tier-ingress -n 3-tier-app-eks
```

Wait 1-2 minutes for the Load Balancer Controller to clean up the ALB.

**Step 2: Destroy Terraform Resources**

```bash
cd terraform
terraform destroy -auto-approve
```

_Note: This will destroy all resources including the EKS cluster and RDS database._

### Local Cleanup

**Docker Compose:**

```bash
docker compose down -v  # -v removes volumes
```

**Kind:**

```bash
kind delete cluster --name three-tier
```

## What I Learned

Keeping everything in Terraform means one source of truth for the entire infrastructure. I started with eksctl for the cluster but ended up with resources in two places which got confusing fast. Moving everything to Terraform means I can understand the whole system without jumping between different tools.

GitOps is worth the initial setup time. Yes it took effort to get ArgoCD working but now deploying is just git push. I do not have to remember kubectl commands or worry about which version is running where. The Git repo is the source of truth.

IRSA is not optional for production workloads. I initially considered giving the EC2 nodes broad IAM permissions but that would have been a security mistake. IRSA means each pod only gets the permissions attached to its ServiceAccount. It is more work upfront but way more secure.

Cost surprises are real. That NAT Gateway cost caught me off guard at thirty two dollars per month just so private subnets can reach the internet. Worth knowing about before you deploy.
